# FTS5 与中文分词

> 上级：[[04-AI与职业/04.01-AI学习/04.01.07-检索实操/04.01.07-检索实操|04.01.07-检索实操]]

## 一、实测：默认分词器查不到中文

在 SQLite 里直接试（本地版本 3.50.4）：

| 分词器 | 查 ``缓存`` | 结论 |
|--------|------------|------|
| ``unicode61``（默认） | ``[]`` | ❌ 中文整段被当成一个 token |
| ``trigram`` | 命中 | ✅ 三字符滑窗，天然支持中文子串 |

``unicode61`` 按"非字母数字"切词，一整句中文中间没有分隔符，于是变成**一个巨大的 token**，
``MATCH '缓存'`` 永远匹配不到。所以中文全文检索必须显式指定分词器：

```sql
CREATE VIRTUAL TABLE chunks USING fts5(
    text,
    source UNINDEXED,
    heading UNINDEXED,
    start_line UNINDEXED,
    end_line UNINDEXED,
    tokenize='trigram'
)
```

## 二、trigram 的边界与回退

trigram 对**少于 3 个字符**的查询无效，所以：

```
查询 "token"   → 长度 ≥3 → 走 trigram
查询 "裁剪"    → 长度 2  → 回退 LIKE '%裁剪%'
查询 "缓存命中" → 长度 4  → 走 trigram
```

回退策略：短词用 LIKE；trigram 无结果时也回退 LIKE。两种路径都存在，才不至于"搜不到就说没有"。

## 三、为什么用 FTS5 而不是每次扫描

早期实现（``note_search.py``）每次检索都遍历目录、重新切块、在内存里算二元组命中数：

| | 每次重扫 | FTS5 索引 |
|--|---------|-----------|
| 首次 | 快 | 建索引慢 |
| 后续每次 | O(全部文件) | O(命中数) |
| 排序 | 命中计数（长块占优） | bm25（考虑词频与文档长度） |
| 持久化 | 无 | 落库，可增量更新 |

笔记库会涨到几十万字，这一步是必须的。

## 四、UNINDEXED 列的用处

把 ``source`` / ``heading`` / 行号作为 ``UNINDEXED`` 列放进同一张虚拟表：
既能随检索结果一起取出（省一次关联查询），又不会被全文索引（省空间、避免误召回）。
