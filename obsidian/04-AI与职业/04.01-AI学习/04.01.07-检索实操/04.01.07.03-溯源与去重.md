## 一、溯源：每条结果都要能回原文

没有行号的检索结果等于"我记得在哪本书里见过"。所以每个命中都带：

```python
hit = index.search('缓存命中')[0]
hit.citation()   # 'agent_learning/README.md:42'
hit.heading      # '缓存 > 命中统计'
hit.start_line, hit.end_line
```

拼进上下文时直接给引用（`format_hits`）：

```
[1] obsidian/03-FastAPI/03.05-Redis缓存/.../03.05.01.01-Redis是什么与数据类型.md:12（Redis > 数据类型）
缓存命中率 = 命中次数 / 总请求次数……
```

用户能核对，模型也更不容易编造——**引用本身就是一种约束**。

## 二、去重：别让同一段话占满 top-k

同一文件相邻块容易一起命中（内容相似），3 个名额被一段话吃掉。
`_drop_overlaps` 的做法是按分数从高到低保留，**行号区间与已保留结果重叠的直接丢弃**：

```python
first = SearchHit('a.md', 'h', 1, 10, 'x', 2.0)
overlapping = SearchHit('a.md', 'h', 5, 15, 'y', 1.0)
# 保留 x，丢弃 y；不同 source 不受影响
```

## 三、排序：标题命中优先

块内命中与标题命中的含义不同——标题命中说明**整块都在讲这件事**。
实现用倍率而不是加法：

```python
score = base_score * (2.0 if heading 命中 else 1.0)
```

为什么用倍率？trigram 下 bm25 的绝对值极小（1e-6 量级），加一个常数会直接压过相关性排序；
倍率则是"在相关性基础上的加权"，与量级无关。

## 四、检索结果怎么进上下文

组装顺序与预算（回顾主题 1、2）：

1. 系统提示（固定）
2. 工具 schema（固定）
3. **检索片段**（按相关度排序，可丢尾部）
4. 最近对话
5. 用户提问

检索片段本身也要按 token 预算裁剪——一条长片段能顶几十轮对话。
