# 为什么需要结构化输出

> 上级：[[04-AI与职业/04.01-AI学习/04.01.06-结构化输出与校验/04.01.06-结构化输出与校验|04.01.06-结构化输出与校验]]

## 一、自由文本不是接口

聊天要"自然"，程序要"确定"。把 LLM 输出直接喂给下游代码，会出现三种失败：

| 失败模式 | 表现 | 例子 |
|----------|------|------|
| 没有 JSON | 模型只给了自然语言 | "我觉得标题应该是……" |
| JSON 语法错 | 括号不配对、尾逗号、被截断 | `{"title": "摘要",}` |
| JSON 合法但语义不合规 | 字段缺失、类型错、枚举越界、多出字段 | `{"confidence": "high"}` |

第三种最危险：**它看起来是对的**，直到上游逻辑在半夜炸掉。

## 二、解析地狱的典型写法

```python
# 不要这样
if '标题' in text:
    title = text.split('标题')[1].split('\n')[0]
```

问题：模型换个表述就崩、没法测试、给不出错误原因、改一次 prompt 就得重写解析。

## 三、换个思路：先定契约

和写后端接口一样——**先定 schema，再让模型往里填**：

```
自然语言 → [契约 schema] → 结构化数据 → 业务逻辑
```

好处：

- 失败**可检测**：校验器会说清哪个字段错
- 失败**可修复**：把错误回喂，模型能改对
- 契约**可测试**：不调模型也能测解析与校验

## 四、一条不可让步的原则

> **校验不通过就重试或抛错，绝不替模型猜。**

"猜"的代价是把错误埋进数据里。宁可这一轮失败，也不要写进去一张半对的卡片。

## 五、什么时候不需要结构化

- 纯聊天、纯润色：自由文本更自然
- 给人读的长文：Markdown 更好

判断标准：**这个输出后面有没有代码读它**。有，就必须结构化。
